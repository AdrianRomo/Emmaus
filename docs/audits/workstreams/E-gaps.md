### 1.1 Notes per module (what to reuse, what couples it)

**Personas.** Three account-creation paths all key on e-mail and refuse or reuse an existing address: `/setup/` (`clean_admin_email`) `[Verified core/forms.py:189-193]`, invitation acceptance ("Ya existe una cuenta con este correo.") `[Verified core/forms.py:449-450]`, and `team.add_member` (`account_for_email` → reuse, else create with an unusable password) `[Verified events/services/team.py:49-50, 80-94]`. **Inference:** "one account per e-mail" is already a de-facto invariant, so "no second account" (J2) is achievable by routing every future creation through one shared helper rather than by a new constraint. What is missing is the *tenant-scoped person without login* and the *explicit link* (vision §5.2 `Person`, `IdentityLink`). `ParticipantProfile` already carries contact preference and consent timestamps `[Verified core/models.py:220-227]`: that is the field set to lift into `Person`.

**Organizaciones/Sedes.** `Sede` is already church-owned and protected (`PROTECT` on `EventParticipant.sede`; delete only without camperos) `[Verified events/models.py:536]`, `[Verified events/views/admin.py:1193-1209]`. The CRUD is mounted inside an event URL (`/eventos/<slug>/administracion/sedes/`) and documented as a known oddity `[Verified docs/roles-and-permissions.md:186]`. **Proposal:** a church-level `/iglesia/sedes/` screen can be added beside it (same form, same service) without removing the event one until after the camp.

**Grupos.** Nothing to reuse at the data level; at the UX level the "one tinted panel with the next question" pattern and the row/list components are reusable `[Verified README.md:8, 14]`. The tutor→coordinador→campero hierarchy (`TutorAssignment`, `EventAccess.supervised_coordinator_ids`) `[Verified events/access.py:99-141]` is the closest *scoping* pattern: a leader sees exactly the people of their own unit, derived from explicit assignment rows, never inferred from names.

**Seguimiento.** `FollowUpRequest.Source` already models "participant_request" and "inactivity" `[Verified core/models.py:422-426]`; `by_state` ordering and `complete_follow_up` are small and generic `[Verified core/views.py:125-136, 840-852]`. Keep `events.FollowUp` untouched (camp, confidential).

**Mi Iglesia.** The context processor builds role-specific nav lists and `show_events_link` `[Verified core/context_processors.py:14-83]`; it will need a branch for "has a Person in this church" rather than "has a church role".

**Reportes.** `suppress()` and `release_cells()` are pure functions with tests `[Verified events/tests/test_reporting.py:119-148]`; `AuditEvent.event` is already nullable `[Verified events/models.py:1162]`, so non-event audit rows are possible without a migration (a `church` column would still be needed to list them per tenant).

## 6. First implementation PR/epic (Proposal, not implemented)

**Epic:** "Foundations, step 1 — `Person` and `IdentityLink` (additive, invisible, zero camp impact)". Issue form fields per `docs/agents/workflow.md:63-73`; label `risk:medium`, `area:v2`; one session; draft PR against `v2/foundation`.

**Scope in:** ADR 0002 (P1-1); `core/models.py`: `Person` (church FK, `first_name`, `last_name`, `email` blank, `phone` blank, `preferred_contact_method` copied from `ParticipantProfile.ContactMethod`, `created_from` choices `setup/invitation/team/backfill/manual`, `created_at`) and `IdentityLink` (`user`, `person`, `church`, `created_at`; unique `(church, user)`, unique `(person)`); one additive migration + one data migration that backfills a `Person` and link for every `ParticipantProfile` and every `UserChurchRole` holder, reverse no-op; read-only Django admin; `core/persons.py` with `persons_for(user)` (church-scoped queryset helper); tests.
**Scope out:** any view, template, URL, nav item, change to `events/`, change to `User` creation paths, any `Person` for an `EventParticipant`.

**Why it is the safest start.** It is the one dependency of every P2 item (F5) and of J3/J6, yet it changes no behaviour: no view reads it, so every existing test, the browser gate and the camp screens are untouched; the migration adds tables only (`risk:medium`, not a camp table `[Verified docs/agents/policies.md:13-14]`); the reverse is a no-op data step plus dropping two new tables (`[Verified docs/deployment.md:320-342]` rollback pattern); it does not touch `events/access.py` or `core/access.py`, so it needs no authorization escalation `[Verified docs/agents/policies.md "Escalate"]`; and it settles the identity vocabulary (vision §5.2) before anyone builds groups on `User`.

**Acceptance tests (pytest, SQLite and PostgreSQL):**

## 8. Top 5 for the synthesis

1. **No person/identity layer is the blocking gap.** Camperos are event-owned rows without accounts or contact fields; discipleship participants are Django users; nothing links them (F5). J2 step 4 cannot be built on today's tables. Start with an additive `Person` + `IdentityLink` PR (§6) and link camperos through a separate table after the camp, never by editing `EventParticipant` or by name matching.
2. **Roles are one-per-scope in two unlinked systems, and church roles imply event roles** (F2–F4). J3/J6 need `RoleAssignment` for *new* scopes plus an explicit current church, delivered as a compatibility layer that leaves `events/access.py` and `core/access.py` untouched before the camp; AGENTS.md invariants 1–2 must be reworded now (docs only).
3. **The sensitive-data boundary is the asset, and it already satisfies J2.7 by construction** (F7). Groups must live entirely outside `events`, group leadership must never be a `UserChurchRole` or an `EventMembership`, and the groups PR must ship the enumerated negative tests (P2-7).
4. **Multi-tenancy is a short list of seams, not a rewrite** (F6): `/setup/`, first-active-church landing/brand, `churches[0]` on create, globally unique event slug and cross-church join lookup, cross-tenant Django admin. All but the public-URL namespaces can be fixed additively; the namespace change waits for the camp to end.
5. **Nothing in application code must be fixed before the camp from this workstream's evidence.** The pre-camp items are infra and docs (`.nodeploy`, branch protection, edge rate limiting, invariant wording, a recorded gate baseline, an operational checklist). Build the community MVP behind `Church.community_enabled`, reusing the `AccessRequest` pattern, the `FollowUpRequest` shape, content-free notifications and the suppression helpers.
